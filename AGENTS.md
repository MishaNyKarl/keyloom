# AGENTS.md — правила разработки Keyloom

Эти правила действуют во всём репозитории для разработчиков и AI-агентов. Более локальный AGENTS.md может уточнять правила своего каталога. Явные инструкции владельца задачи имеют приоритет; исключения нужно объяснять в итоговом отчёте или PR.

## 1. Работа над задачей

- Перед изменениями прочитай README, релевантный код, тесты и состояние Git. Не перезаписывай чужие незакоммиченные изменения.
- Сначала определи ожидаемое поведение и критерии готовности. При неоднозначности используй безопасное обратимое решение; уточняй вопросы, влияющие на данные, публичные контракты или архитектуру.
- Делай минимальное законченное изменение. Не добавляй несвязанный рефакторинг, массовое форматирование или зависимости ради гипотетических задач.
- Сохраняй рабочее приложение на каждом логическом этапе. Не оставляй заглушки вместо заявленных функций.
- Для крупных изменений заранее опиши границы, совместимость, миграцию и способ проверки. Существенные архитектурные решения фиксируй в `docs/decisions/` с контекстом, вариантами и последствиями.
- Не заявляй об успешной проверке, которую не запускал. Укажи непроверенные сценарии и реальные ограничения.

## 2. Архитектура

- Сохраняй разделение: чистые расчёты в `core.js`/`analytics.js`, DOM-адаптер в `content.js`/`configuration.js`, Chrome API и сохранение в `background.js`, отображение в dashboard/popup.
- Не импортируй DOM и Chrome API в вычислительное ядро. Время, случайность и другие изменчивые зависимости передавай параметрами, когда от них зависит тестируемое поведение.
- Используй текущие classic scripts/IIFE для расширения и ESM `.mjs` для Node-инструментов. Переход на сборщик или другую модульную систему требует отдельного обоснования.
- Не создавай второй источник истины для профиля, схемы данных, лимитов или вычисления метрики.
- При изменении контракта сообщения обновляй отправителя, получателя, валидацию и тесты вместе.
- Новые зависимости должны решать конкретную проблему. Обоснуй размер, лицензию, сопровождение и работу офлайн. Если появятся npm-зависимости, коммить lockfile и используй `npm ci` в CI.

## 3. Стиль кода

- UTF-8, LF, финальная новая строка, отступ 2 пробела; правила редактора в `.editorconfig`.
- JavaScript: `const` по умолчанию, `let` только при переназначении, без `var`; одинарные строки, точки с запятой, строгое сравнение.
- `camelCase` для функций и переменных, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант конфигурации. Имена должны описывать предметную область, не способ реализации.
- Пиши многострочный читаемый код: одно действие на строку, фигурные скобки у управляющих блоков, без вложенных тернарных цепочек. Ориентир — 100 символов в строке; не ломай строки и URL механически.
- Новые HTML/CSS пиши в развёрнутом виде. Существующие компактные файлы улучшай в пределах изменяемого участка, а массовое форматирование делай отдельным коммитом.
- Выделяй функцию, когда это уменьшает сложность или дублирование. Не создавай абстракции для единственного тривиального вызова.
- Используй `async/await`; обрабатывай отклонения Promise на границах. Не проглатывай ошибки без обоснованного восстановления и понятного статуса для пользователя.
- Комментарии объясняют причины, ограничения и необычные контракты. Код, имена и технические комментарии — на английском; интерфейс и документация проекта — на русском.
- Не редактируй `extension/vendor` вручную. Обновление vendored-кода — отдельное изменение с версией, происхождением и лицензией.

## 4. Данные и безопасность

- Приватность по умолчанию: без телеметрии, отправки истории, удалённого исполнения кода и расширения области захвата ввода без явно согласованной продуктовой задачи.
- Захватывай только доверенные события поля теста на разрешённом origin. Не превращай адаптер в универсальный сборщик клавиатуры.
- Проверяй origin отправителя, тип сообщения, форму и ограничения данных на границах доверия. Импорт JSON и сообщения страницы считай недоверенными.
- Сохраняй сериализацию read-modify-write операций и дедупликацию результатов. Тестируй конкурентные вкладки и повторную доставку.
- Не меняй формат сохранённых данных без обратной совместимости или явной миграции. Миграция должна быть тестируемой и сохранять пользовательскую историю; не очищай данные ради исправления ошибки.
- Не сохраняй сырой ввод, токены, личные экспорты или пользовательские данные в репозитории, логах и фикстурах. Используй синтетические примеры.
- DOM-текст вставляй через `textContent` и безопасные DOM API. Не используй `innerHTML` для внешних данных, `eval`, inline scripts и удалённые скрипты. Сохраняй CSP и минимальные permissions MV3.
- Не коммить секреты, `.env`, локальные профили браузера, архивы сборки и временные артефакты. Не назначай лицензию собственному коду без решения владельца.

## 5. Тесты и проверки

- Любое изменение расчётов, жизненного цикла теста, хранения, импорта или контракта сообщений сопровождай поведенческими тестами на `node:test`.
- Для исправления ошибки добавляй регрессионный тест, воспроизводящий исходный сбой. По возможности сначала убедись, что он падает без исправления.
- Проверяй наблюдаемое поведение, а не копию реализации. Не подменяй тестируемый алгоритм моками; подменяй только внешние границы, например Chrome API или DOM.
- Тесты должны быть воспроизводимыми: фиксируй часы, случайность и входные данные; не используй сеть, личные аккаунты, случайные задержки и реальные пользовательские данные.
- Для аналитики покрывай пустую и малую выборку, границы, языки и раскладки, прерванные тесты, неверные данные и порядок событий.
- Для адаптера проверяй обычное завершение, промежуток между исчезновением ввода и появлением результата, перезапуск, смену слов и отсутствие ложной привязки упражнения.
- Для хранения проверяй дубли, лимиты, конкурентную запись, выключенный сбор и совместимость экспорта/импорта.
- Для UI проверяй пустое состояние, фильтры, навигацию с клавиатуры, подписи элементов и узкую ширину. Изменения интеграции дополнительно проверяй на установленном расширении, если среда это позволяет; иначе явно отмечай этот пробел.
- Перед коммитом исполни `node --test` и `node scripts/check.mjs`. Не отключай и не ослабляй тесты ради зелёного результата.
- Для чисто документационных правок не создавай искусственные тесты: проверь команды, ссылки и соответствие реализации. Проверки CI всё равно должны проходить.
- CI сейчас проверяет тесты и статические ограничения, но не форматирование и не реальный браузер. Не представляй его как полную гарантию корректности.

## 6. Git и коммиты

- Постоянное указание владельца: каждый запрос, который приводит к изменениям в проекте, по умолчанию заканчивай проверками, коммитом и push в удалённый репозиторий. Дополнительное подтверждение не требуется, если пользователь явно не попросил обратного (например, «не коммить», «без push», «только локально»).
- Отправляй изменения в тематическую ветку и создавай или обновляй PR в `main`. Сам commit/push не означает разрешения на автоматическое слияние PR.
- Если запрос не меняет файлы, не создавай пустой коммит. Не включай чужие или несвязанные изменения. При блокирующей ошибке проверок или push исправь её, если возможно; иначе явно сообщи, что осталось не отправлено и почему.
- В финальном ответе указывай результат публикации: короткий hash коммита и ветку либо ссылку на PR. Не считай запрос с изменениями завершённым, пока push не выполнен или конкретный блокер не объяснён.
- После первоначальной публикации работай в тематических ветках: `feat/<topic>`, `fix/<topic>`, `docs/<topic>`, `chore/<topic>`. Для веток, создаваемых Codex, используй `codex/<topic>`.
- Один коммит — одно логическое изменение. Отделяй массовое форматирование, обновление зависимости и рефакторинг от изменения поведения.
- Используй Conventional Commits: `<type>(<scope>): <description>`. Scope опционален, описание на английском в повелительной форме, без точки в конце; весь заголовок до 72 символов.
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `style`, `perf`, `build`, `ci`, `chore`, `revert`. `style` — форматирование без изменения поведения; визуальная функциональность — `feat` или `fix`.
- Scopes по подсистемам: `capture`, `analytics`, `practice`, `dashboard`, `storage`, `extension`, `tooling`.
- Примеры: `feat(practice): add duration-based exercises`, `fix(capture): preserve completed test status`, `test(storage): cover concurrent saves`.
- Для несовместимого изменения используй `!` и пояснение `BREAKING CHANGE:` в теле с планом миграции. Совместимость данных важна даже в alpha.
- Тело коммита объясняет проблему, решение и существенные ограничения, если заголовка недостаточно. Не включай секреты, личные данные и неподтверждённые заявления.
- Перед коммитом проверяй `git diff --check`, staged diff и список файлов. Не используй `git add .` без предварительного просмотра содержимого.
- Не выполняй force push, переписывание опубликованной истории, удаление веток и чужих изменений без отдельного явного разрешения. Разрешение на обычные commit/push уже дано владельцем в постоянном указании выше.

## 7. Pull requests и готовность

- После начального наполнения репозитория используй PR для изменений в `main`. Заголовок PR также соответствует Conventional Commits; предпочтительный способ слияния — squash.
- В описании укажи проблему, новое поведение, проверки и риски/миграции. Для UI приложи снимок экрана, если он помогает проверить изменение. Используй шаблон PR.
- Изменения контрактов, приватности, схемы данных и permissions требуют явного внимания ревьюера. Защиту веток и обязательные approvals настраивает владелец; этот документ сам их не включает.
- Готово означает: критерии задачи выполнены, необходимые тесты и CI проходят, документация актуальна, нет случайных файлов, ограничения честно указаны.
- При релизе синхронизируй версии `package.json`, manifest и видимой версии интерфейса. Формат данных версионируется отдельно от версии продукта.
- Артефакт расширения содержит только `extension/`; не включай стенд, тесты, экспорт истории и инструменты разработки. Проверяй установку распакованного артефакта перед объявлением релиза проверенным.
